# گزارش پیاده‌سازی ۲۰۱ ماژول مستقل بک‌اند ARIA
تاریخ: 2026-11-19
شاخه: `engineering/aria-preserve-all-capabilities-2026-11-19`

## نتیجه موجودی
در کنار 639 شناسه canonical و تمام رجیستری‌های تاریخی، 197 ماژول مستقل افزایشی از چهار خانواده اصلی و 4 موتور تکمیلی عملیات خدمات ثبت شده‌اند:

| خانواده | تعداد | شناسه/منبع |
|---|---:|---|
| 50 ایده فهرست‌شده در سند 54 ایده | 50 | `ARIA-IDEA-BACKLOG-001..050` |
| چهار کنترل حاکمیتی | 4 | `ARIA-CONTROL-MODULE-001..004` |
| ورودی‌های کاتالوگ تجاری | 72 | `ARIA-CATALOG-651..722` |
| موتورهای فرزند | 71 | `ARIA-ENGINE-MODULE-001..071` |
| چهار موتور تکمیلی عملیات خدمات | 4 | `ARIA-SVC-SUPPORT`, `ARIA-SVC-SUCCESS`, `ARIA-SVC-PACKAGES`, `ARIA-SVC-UNIT-ECONOMICS` |
| **مجموع فایل‌های مستقل بک‌اند** | **201** | 197 + 4 |

این 201 مورد، 201 شناسه canonical جدید نیستند. شناسه‌های 639تایی بدون تغییر باقی می‌مانند؛ رجیستری 893 واحدی نیز بدون بازنویسی یا کاهش حفظ شده است. هیچ‌کدام از 201 ماژول به‌عنوان Production Verified اعلام نشده‌اند.

## ساختار کد
- `backend/aria-module-runtime.cjs`: هسته مشترک اعتبارسنجی قرارداد، tenant context، digest ورودی، طرح عملیات و audit record.
- `backend/modules/ideas/`: 50 فایل مستقل ایده.
- `backend/modules/controls/`: چهار فایل مستقل کنترل.
- `backend/modules/catalog/`: 72 فایل مستقل کاتالوگ.
- `backend/modules/engines/`: 71 فایل مستقل موتور فرزند.
- `backend/modules/service-engines/`: چهار موتور تکمیلی با منطق دامنه‌ای تخصصی.
- `backend/modules/index.cjs` و `backend/modules/index.js`: بارگذاری، کنترل یکتایی شناسه و کنترل شمارش دقیق خانواده‌ها.

هر ماژول manifest جداگانه، شناسه مستقل، ورودی/خروجی، عملیات، lineage و ارتباط والد/میزبان خود را دارد. زیرساخت مشترک فقط در runtime reuse می‌شود؛ قراردادهای دامنه‌ای در فایل‌های مستقل باقی می‌مانند.

## API و ذخیره‌سازی
- `GET /api/aria-modules/catalog`: کاتالوگ 201 ماژول و شمارش هر خانواده.
- `POST /api/aria-modules/{moduleId}/execute`: اجرای گردش‌کار محلی با احراز هویت و هدر `Idempotency-Key`.
- `GET /api/aria-modules/{moduleId}/work-items`: دریافت سوابق همان حساب.
- `POST /api/aria-modules/{moduleId}/work-items/{workItemId}/actions`: تغییر وضعیت کنترل‌شده برای موتورهای خدمات.

جدول `aria_modular_work_items` با کلید یکتای کاربر/tenant/ماژول/idempotency ایجاد می‌شود. برای جلوگیری از ذخیره غیرضروری ورودی خام، digest و فهرست فیلدهای ورودی در artifact ثبت می‌شود. خروجی محلی و audit record ذخیره می‌شوند.

**مرز tenant فعلی:** `tenant_id` برابر شناسه حساب احراز‌شده است. این جداسازی حساب‌محور است، نه tenant سازمانی چندکاربره؛ نقش‌ها و RLS سازمانی هنوز نیازمند تکمیل و آزمون زنده‌اند.

## تکمیل چهار موتور باقی‌مانده

### 1. پشتیبانی و تعهد خدمت
- ایجاد پرونده پشتیبانی با اولویت و هدف زمانی پاسخ.
- ارزیابی SLA به‌صورت `ON_TRACK / OVERDUE / RESOLVED`.
- گردش وضعیت `OPEN → IN_PROGRESS → WAITING_CUSTOMER → RESOLVED` و امکان بازگشایی.
- اتصال پرونده پشتیبانی به پرونده خدمت متعلق به همان حساب.
- ارسال پیام/اعلان بیرونی هنوز انجام نمی‌شود؛ ارزیابی SLA فعلاً هنگام درخواست انجام می‌شود و worker زمان‌بندی‌شده ندارد.

### 2. موفقیت مشتری و تمدید
- محاسبه سلامت دوره‌ای از روزهای فعالیت، کارهای تکمیل‌شده، هدف و درخواست‌های حل‌نشده.
- خروجی `HEALTHY / NEEDS_ATTENTION / AT_RISK`.
- گزارش شاخص‌ها صریحاً «داده ورودی کاربر، تأییدنشده مستقل» علامت می‌خورد.
- توصیه تمدید فقط پس از تأیید مالک ثبت می‌شود؛ تمدید خودکار یا برداشت وجه وجود ندارد.

### 3. بسته‌های خدمت و گردش‌کار
- ساخت بسته نسخه‌دار از شناسه‌های خدمات ARIA.
- گردش `DRAFT → REVIEW_PENDING → APPROVED → PUBLISHED_LOCAL` و بایگانی.
- تأیید و انتشار محلی نیازمند تأیید مالک است.
- انتشار عمومی، فعال‌سازی entitlement و دریافت وجه انجام نمی‌شود.

### 4. هزینه و سودآوری خدمت
- محاسبه هزینه ارائه‌دهنده، مدل، ذخیره‌سازی، پشتیبانی و پرداخت.
- محاسبه contribution margin و درصد آن.
- درآمد پلتفرم از اصل وجوه مشتری/فروشنده جداست؛ اصل وجوه در درآمد ARIA منظور نمی‌شود.
- خروجی فعلی محاسبه از داده ورودی است، نه ledger یا تسویه بانکی تأییدشده.

## کنترل‌های امنیتی و حاکمیتی
- احراز هویت برای اجرا، مشاهده سابقه و تغییر وضعیت.
- جداسازی حساب در queryهای ذخیره‌سازی.
- کلید idempotency اجباری برای اجرای ماژول.
- کنترل مالک برای Autonomy Control Center، Owner Control Center، تأیید تمدید و انتشار محلی بسته.
- Intent Marketplace نیازمند فیلد رضایت صریح است.
- اجرای بیرونی، پرداخت، انتشار پیام یا provider در این runtime فعال نیست.

## آزمون‌ها و وضعیت تأیید
آزمون‌های زیر به مخزن افزوده/گسترش یافته‌اند:
- `test/aria-modular-registry.test.js`: تعداد 201، یکتایی شناسه‌ها، قرارداد اجرا و چهار موتور خدمات.
- `test/aria-service-extended-engines.test.js`: ورودی‌های نامعتبر، SLA، انتقال وضعیت، تأیید تمدید، چرخه بسته و محاسبه اقتصاد واحد.
- `test/aria-service-delivery-api.test.js`: کاتالوگ API، تعداد ماژول‌ها و رد درخواست بدون احراز هویت.

Workflow موجود `aria-ci.yml` در push به همین شاخه باید `npm run check`، `node --check backend/aria_expansion_runtime.cjs` و `npm test` را اجرا کند. با این حال، در آخرین استعلام برای commitهای جدید، GitHub status check و workflow run قابل مشاهده برنگرداندند؛ بنابراین اجرای موفق آزمون‌ها را ادعا نمی‌کنیم. این تست‌ها نوشته شده‌اند، اما PASS بودنشان هنوز نیازمند run واقعی است.

## مواردی که هنوز Production را مسدود می‌کنند
1. اجرای CI و رفع هر خطا؛ به‌ویژه بارگذاری 201 فایل و startup guard شمارش.
2. آزمون PostgreSQL زنده برای migration، ذخیره، بازیابی، rollback و idempotency هم‌زمان.
3. آزمون جداسازی tenant و طراحی tenant سازمانی/RLS.
4. آزمون امنیتی کنترل‌های مالک، MFA و نقش‌ها.
5. providerها، اعلان بیرونی، PSP، webhook، بازپرداخت و ledger واقعی.
6. backup/restore، staging، E2E، Android build/signing و device UAT.
7. crosswalk معنایی نهایی با 639 canonical، 81 موتور زیرساختی و سایر overlayها؛ شناسه‌های موقت بدون تأیید به canonical ارتقا نمی‌یابند.

**وضعیت نهایی این تغییر:** 201 فایل ماژول و API/ذخیره‌سازی محلی به شاخه توسعه اضافه شده‌اند؛ CI، PostgreSQL زنده، E2E و Production هنوز تأیید نشده‌اند. PR باید Draft و Unmerged باقی بماند تا گیت‌های انتشار واقعاً پاس شوند.
