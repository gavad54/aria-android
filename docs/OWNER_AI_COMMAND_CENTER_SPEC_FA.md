# مشخصات اجرایی مراکز مدیریت مالک و فرماندهی هوش مصنوعی

وضعیت این سند: قرارداد معماری برای پیاده‌سازی در این مخزن؛ وجود این سند به‌تنهایی به معنی تکمیل قابلیت‌ها نیست.

## 1. دامنه
این محصول دو مرکز مستقل دارد:
- OWNER CONTROL CENTER: مدیریت مالک، کاربران مدیریتی، تنظیمات، مجوزها، ماژول‌ها و موتورهای درآمدی.
- AI COMMAND CENTER: پایش، تشخیص، تحلیل علت ریشه‌ای، پیشنهاد اصلاح، آزمون، کنترل سازگاری و پایش پس از انتشار.

این دو مرکز در همین محصول اجرا می‌شوند و نباید به محصول دیگری یا یک مرکز فرماندهی مادر وابسته باشند.

## 2. توسعه‌پذیری در زمان اجرا
مالک باید بتواند از پنل خود:
1. ماژول جدید را با شناسه یکتای تغییرناپذیر ثبت کند.
2. نام، شرح، دسته، نسخه، مالکیت محصول، وضعیت و وابستگی‌ها را تعیین کند.
3. موتور درآمدی جدید را با شناسه یکتا، مدل درآمد، واحد قیمت‌گذاری، تعرفه، دوره صورتحساب، شرایط فعال‌سازی و وضعیت انتشار تعریف کند.
4. ماژول/موتور را ابتدا در حالت draft نگه دارد، سپس در محیط آزمایشی بررسی و پس از تأیید فعال کند.
5. قابلیت را تعلیق یا بازنشسته کند؛ حذف سخت سوابق و داده‌های مالی ممنوع است.

افزودن یک رکورد به فهرست به‌تنهایی کافی نیست؛ هر ماژول باید قرارداد اجرایی، مجوزها، رویدادها، آزمون سلامت و رابط اتصال مشخص داشته باشد.

## 3. حداقل مدل داده
### product_modules
- id (UUID/شناسه یکتا)
- module_key (unique, immutable)
- name, description, category
- version, status: draft | validating | enabled | suspended | deprecated
- manifest_json (قرارداد، قابلیت‌ها و تنظیمات معتبر)
- dependencies_json
- permissions_json
- created_by, approved_by, created_at, updated_at

### revenue_engines
- id (UUID/شناسه یکتا)
- engine_key (unique, immutable)
- name, description, revenue_model
- pricing_unit, pricing_config
- billing_period, currency
- status: draft | validating | enabled | suspended | deprecated
- linked_module_keys
- created_by, approved_by, created_at, updated_at

### change_audit
- id, actor_type, actor_id, action, target_type, target_id
- before_json, after_json, approval_id, correlation_id, created_at

### ai_findings
- id, severity, category, target_type, target_id
- evidence_json, root_cause, proposed_fix
- status: detected | triaged | approved | testing | resolved | rejected
- created_at, resolved_at

## 4. مرز اختیارات
- مالک: تعریف، تأیید، فعال‌سازی، تعلیق، تعیین تعرفه و مجوزهای مدیریتی.
- هوش مصنوعی: خواندن متریک‌ها و لاگ‌های مجاز، تحلیل، پیشنهاد، اجرای آزمون و اصلاحات از پیش مجاز.
- هوش مصنوعی بدون تأیید مالک حق تغییر نقش مالک، حذف داده، تغییر طرح مالی، ایجاد هزینه، تغییر schema تولید یا انتشار تولیدی ندارد.
- کلیدها و اسرار فقط در secret manager/متغیرهای محرمانه نگهداری می‌شوند؛ هرگز در manifest، log یا کد ثبت نمی‌شوند.

## 5. گردش عمر ماژول و موتور درآمدی
ثبت draft → اعتبارسنجی manifest → بررسی مالکیت و مرز محصول → بررسی مجوزها و وابستگی‌ها → اجرای آزمون ایزوله → تأیید مالک → فعال‌سازی کنترل‌شده → پایش → تعلیق/بازگشت در صورت شکست.

تغییر نسخه باید سازگاری عقب‌رو، migration و برنامه rollback داشته باشد. موتور درآمدی تا زمان اتصال و آزمون چرخه قیمت‌گذاری، صورتحساب، تمدید، لغو و گزارش مالی نباید برای مشتری واقعی فعال شود.

## 6. قابلیت‌های AI Command Center
- health checks و پایش uptime/latency/error rate
- جمع‌آوری ساختاریافته لاگ و correlation ID
- دسته‌بندی خطا و تحلیل علت ریشه‌ای با شواهد
- dependency graph و کنترل قرارداد API
- تشخیص ناسازگاری نسخه و ماژول‌های یتیم/تکراری
- اجرای تست‌های واحد، یکپارچه‌سازی، امنیت و smoke در محیط آزمایشی
- پیشنهاد patch و ارائه diff برای بازبینی
- canary/staged rollout و rollback فقط با مجوز
- گزارش وضعیت، شدت، مالک اقدام و زمان رفع

AI نباید صرفاً بر اساس حدس، نتیجه «رفع شد» اعلام کند. رفع فقط پس از آزمون موفق و مشاهده سیگنال سلامت ثبت می‌شود.

## 7. امنیت و ممیزی
- احراز هویت قوی و MFA برای حساب مالک
- RBAC با اصل حداقل دسترسی و جداسازی tenant در صورت وجود چندسازمانی
- ثبت رویداد append-only برای اقدامات مالک و AI
- محافظت CSRF/XSS/SQL injection و rate limiting متناسب با پلتفرم
- اعتبارسنجی schema ورودی و امضای درخواست‌های داخلی
- رمزنگاری انتقال و داده‌های حساس در حالت سکون
- پشتیبان مستقل و آزمون بازیابی
- عدم نمایش اسرار در خطاها و گزارش‌ها

## 8. مرز ارتباط محصولات
اتصال به محصولات دیگر فقط از طریق API نسخه‌بندی‌شده، احراز هویت سرویس‌به‌سرویس، scopes محدود، قرارداد داده و timeout/retry/idempotency انجام می‌شود. دسترسی مستقیم به پایگاه داده محصول دیگر ممنوع است. قطع ارتباط خارجی نباید هسته این محصول را از کار بیندازد.

## 9. معیارهای پذیرش
- مالک بتواند ماژول و موتور درآمدی جدید را بدون تغییر دستی کد هسته ثبت کند.
- ثبت تکراری شناسه یکتا رد شود.
- ماژول ناسازگار یا فاقد مجوز فعال نشود.
- تغییرات حساس بدون تأیید مالک رد شوند.
- AI بتواند خطای آزمایشی را با evidence شناسایی کند و پس از اصلاح تست را دوباره اجرا کند.
- خطا و تغییرات در audit log ثبت شوند.
- تعلیق/rollback قابلیت، داده‌های مالی و سوابق را حفظ کند.
- APIهای داخلی و خارجی دارای تست قرارداد باشند.
- تست‌های امنیتی و جداسازی دسترسی موفق باشند.
- پشتیبان مستقل بازیابی و نتیجه آن ثبت شود.

## 10. وضعیت تحویل
این سند نیازمندی است. پیاده‌سازی فقط پس از افزودن کد، migration، UI، API، آزمون و شواهد CI/محیط آزمایشی قابل اعلام است.

## تطبیق با ARIA
محدوده محصول: خدمات دیجیتال، خدمات AI، استودیوی خلاق و محتوا (NEGAH)، وب‌سایت و صفحات فرود (NAMA) و ابزارهای دیجیتال. حسابداری و ERP در این محصول مجاز نیست.

در مخزن فعلی، API وب Node.js و PostgreSQL در README معرفی شده‌اند؛ پیاده‌سازی backend باید ابتدا ساختار واقعی routeها، migrationها، middleware احراز هویت و تست‌های موجود را بررسی و از همان الگو استفاده کند. رابط فارسی RTL و mobile-first حفظ شود. اگر Android source هنوز در مخزن نیست، این قابلیت نباید به‌عنوان پیاده‌سازی Android گزارش شود.

موتورهای درآمدی مجاز: اشتراک خدمات دیجیتال، ساخت وب/صفحه، تولید رسانه، پروژه‌های AI، آموزش دیجیتال و بسته‌های محتوا. هر موتور باید به قابلیت/خدمت ARIA متصل باشد و صورتحساب رسمی حسابداری را به ARIA اضافه نکند.
