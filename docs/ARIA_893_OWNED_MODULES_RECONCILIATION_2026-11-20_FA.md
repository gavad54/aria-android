# ممیزی و تکمیل موجودی ۸۹۳ واحد متعلق به ARIA — ۲۰۲۶-۱۱-۲۰

## تصمیم شمارش

هدف ۸۹۳ واحد متعلق به ARIA است؛ ۳۹ رکوردی که مالکیت آن‌ها به ARVAND، ARMIN MARKET، LEADORA یا آرشیو تعلق دارد، همچنان فقط lineage هستند و به ARIA بازگردانده نمی‌شوند.

| گروه | تعداد | مالکیت/نقش |
|---|---:|---|
| Canonical baseline | ۶۳۹ | ARIA؛ شناسه‌ها immutable |
| Overlay تاریخی متعلق به ARIA | ۷۲ | ARIA؛ از ۱۱۱ رکورد اصلی پس از جداسازی مالکیت |
| کاتالوگ تجاری | ۷۲ | ARIA؛ روی قراردادهای میزبان canonical |
| موتورهای زیرمجموعه | ۷۱ | ARIA؛ فرزند ماژول‌های دامنه |
| ماژول‌های افزوده جدید | ۳۹ | ARIA؛ شناسه‌های مستقل جدید |
| **جمع واحدهای متعلق به ARIA** | **۸۹۳** |  |
| lineage منتقل‌شده/آرشیوی | ۳۹ | خارج از مالکیت ARIA |
| **کل رکوردهای رجیستری سلسله‌مراتبی** | **۹۳۲** | ۸۹۳ متعلق به ARIA + ۳۹ lineage |

فرمول:
- واحدهای متعلق به ARIA: ۶۳۹ + ۷۲ + ۷۲ + ۷۱ + ۳۹ = ۸۹۳
- کل رجیستری: ۸۹۳ + ۳۹ lineage = ۹۳۲

## ۳۹ ماژول افزوده جدید

۳۹ ماژول با شناسه‌های `ARIA-OWNED-ADDITIONAL-001..039` اضافه شده‌اند. دامنه‌ها شامل برنامه‌ریزی مالی شخصی، مسیر شغلی، موجودی کسب‌وکار، خدمات مشتری، نوبت‌دهی، رویداد، سفر، کشف خدمات محلی، دسترس‌پذیری دیجیتال، مدیریت واژگان، دانش، پژوهش، آموزش، داوطلبان، شفافیت اجتماعی، تعمیر، انرژی، پسماند، کشاورزی، تدارکات، زنجیره تأمین، بازبینی اسناد، فرم، نظرسنجی، کیفیت، ریسک، انطباق، اتصال‌دهنده‌ها، حریم خصوصی، پشتیبان‌گیری، بومی‌سازی، انتشار، دارایی دیجیتال و خدمات پس از فروش است.

هر رکورد دارای شناسه یکتا، مالک، دامنه، ورودی، خروجی، گام‌های گردش‌کار، معیار پذیرش، شاخص سنجش، سیاست دسترسی و مدل درآمدی پیشنهادی است. اجرای فعلی این ۳۹ مورد در مرز `LOCAL_WORK_ITEM_ONLY` است؛ این یعنی ساخت و ذخیره گردش‌کار محلی، نه اجرای خودکار سرویس بیرونی.

## Runtime و API

- `backend/aria-039-replacement-runtime.cjs`: اعتبارسنجی شناسه، tenant، actor، هدف و اندازه context؛ آماده‌سازی گام‌های محلی و audit record.
- `GET /api/aria-expansion/additional-modules`: فهرست ۳۹ ماژول افزوده.
- `POST /api/aria-expansion/additional-modules/:moduleId/run`: اجرای کنترل‌شده و ذخیره work item با احراز هویت و اتصال به tenant حساب جاری.
- `backend/aria-144-domain-runtime.cjs`: رجیستری ۷۲ overlay متعلق به ARIA و ۷۲ ماژول تجاری؛ برای ۷۲ ماژول تجاری، dispatch به ماژول‌های مستقل backend انجام می‌شود. overlay تاریخی در مرز work-item محلی آماده می‌شود.
- APIهای summary، inventory، capability matrix و execution registry تعداد ۸۹۳ واحد ARIA و ۹۳۲ رکورد کل را جداگانه گزارش می‌کنند.

## وضعیت واقعی بلوغ

- ۶۳۹ canonical: قرارداد و مسیر workflow ثبت شده؛ اجرای E2E همه قابلیت‌ها اثبات نشده است.
- ۷۲ overlay: مسیر ایجاد work item محلی موجود است؛ این مسیر به‌تنهایی اجرای کامل عملیات دامنه یا سرویس بیرونی نیست.
- ۷۲ تجاری: قراردادهای دامنه و handlerهای محلی backend دارند؛ پرداخت زنده و monetization هنوز فعال نیست.
- ۷۱ موتور: ماژول‌های backend و parent mapping دارند؛ وجود موتور/قرارداد به معنی اتصال provider یا اجرای E2E نیست.
- ۳۹ افزوده: workflow محلی tenant-scoped و work item قابل ثبت آماده می‌کنند؛ هنوز E2E/Production verified نیستند.
- ۳۹ lineage: غیرقابل اجرا از ARIA؛ مالکیت محصولات مقصد حفظ می‌شود.
- شمار Production verified در رجیستری همچنان صفر باقی می‌ماند تا شواهد واقعی فراهم شود.

## گیت‌های باقی‌مانده برای تأیید نهایی

1. CI کامل روی head جدید باید PASS شود.
2. تست یکپارچه با PostgreSQL واقعی و tenant isolation/RLS لازم است.
3. برای ماژول‌هایی که خروجی نهایی به provider نیاز دارند، اتصال رسمی، مجوز محدود، مدیریت secrets، rate limit و retry/idempotency لازم است.
4. پرداخت فقط پس از انتخاب و اتصال PSP، تست sandbox، تأیید مالک، رسید معتبر و reconciliation فعال می‌شود.
5. backup و restore واقعی، E2E، UAT، آزمون دستگاه Android و ممیزی امنیتی Production باید جداگانه اثبات شوند.

هیچ‌یک از این گیت‌ها با تعداد رجیستری یا تست unit جایگزین نمی‌شوند. وضعیت Production فقط با شواهد قابل بازبینی ارتقا می‌یابد.

## مدل درآمدی ۳۹ ماژول افزوده
برای هر ۳۹ ماژول، قرارداد درآمدی مستقل ثبت شده است: entitlement key، روش‌های بالقوه دریافت (اشتراک/اعتبار/هر کار تکمیل‌شده)، واحد metering، سیاست قیمت‌گذاری تحت کنترل مالک، محدودیت مصرف، سیاست بازپرداخت، افشای مالیات و کارمزد، ضدتقلب و قاعده شناسایی درآمد فقط پس از رویداد پرداخت معتبر. مبلغ و ارز عمداً خالی‌اند تا مالک قیمت‌گذاری کند. درگاه پرداخت متصل نیست و billing/payment خاموش است؛ بنابراین این مرحله آماده‌سازی تجاری است، نه درآمد زنده.

## رجیستری تجاری یکپارچه ۸۹۳ واحد
- فایل `backend/data/aria_893_commercialization_registry.json` برای تمام ۸۹۳ واحد متعلق به ARIA قرارداد دسترسی/درآمد تعریف می‌کند.
- ۶۳۹ canonical، ۷۲ overlay، ۷۲ ماژول تجاری و ۳۹ ماژول افزوده، entitlement مستقل قابل قیمت‌گذاری دارند: جمع ۸۲۲ entitlement.
- ۷۱ موتور فرزند به entitlement والد متصل‌اند و جداگانه صورتحساب نمی‌شوند تا دوباره‌فروشی یا دوباره‌صورتحساب رخ ندهد.
- API خواندنی `GET /api/aria-expansion/commercialization-registry` رجیستری را ارائه می‌دهد.
- `POST /api/aria-expansion/commercialization/usage-preview` با احراز هویت، preview مصرف tenant-scoped تولید می‌کند؛ رویداد preview به‌تنهایی ثبت پایدار، صورتحساب یا برداشت وجه نیست.
- همه قیمت‌ها/ارزها تحت سیاست `OWNER_CONFIGURED` خالی مانده‌اند. billing، payment و revenue recognition غیرفعال‌اند تا PSP واقعی، سیاست قیمت، مجوز مالک و تطبیق پرداخت فراهم شود.

## ممیزی هم‌پوشانی و مرزبندی دامنه ۳۹ ماژول افزوده
برای جلوگیری از افزایش عدد با ماژول‌های تکراری، نام/شرح/عملیات ۹ مورد نزدیک به قابلیت‌های قبلی تخصصی‌تر شد و Crosswalk آن‌ها در رجیستری ثبت شد:
- مربی مصاحبه و ارزیابی درخواست استخدام ← مرتبط با مسیر شغلی؛ محدود به درخواست استخدام و تمرین مصاحبه.
- هماهنگ‌کننده سفر گروهی و اختلالات مسیر ← مرتبط با برنامه‌ریز سفر؛ محدود به وابستگی گروه و اختلال سفر.
- ارزیاب شواهد اعتبار ارائه‌دهنده ← مرتبط با کشف خدمات؛ محدود به بررسی مدارک و شواهد.
- برنامه‌ریز آزمون فناوری‌های کمکی ← مرتبط با ممیزی دسترس‌پذیری؛ محدود به ماتریس آزمون فناوری کمکی.
- سامانه سنجش و ارزیابی مهارت زبان ← مرتبط با مربی زبان؛ محدود به سنجش و گزارش سطح.
- مدیریت بایگانی و نگهداری سوابق ← مرتبط با گردش تصویب اسناد؛ محدود به چرخه عمر و retention.
- مدیریت درخواست دسترسی و حقوق داده ← مرتبط با ارزیابی اثر حریم خصوصی؛ محدود به درخواست‌های صاحب داده.
- کنترل کیفیت چیدمان RTL و بومی‌سازی رابط ← مرتبط با ترجمه؛ محدود به QA قالب‌بندی و جهت نوشتار.
- ثبت تصمیم و زنجیره شواهد سازمانی ← مرتبط با کیوریشن دانش؛ محدود به decision log و lineage شواهد.
تمام ۳۹ رکورد اکنون دارای scopeBoundary و وضعیت crosswalk هستند. این بررسی یک ممیزی متنی/قراردادی است؛ تأیید نهایی عدم هم‌پوشانی نیازمند بازبینی محصول و E2E هر دامنه است.
